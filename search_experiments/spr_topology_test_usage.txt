spr_topology_test -- command reference
=======================================

Standalone test/exploration executable for the modern SPR (subtree pruning
and regrafting) API declared in tree/phylotree.h and implemented in
tree/phylotree.cpp (isLegalSPR / applySPR / rollbackSPR). Source:
tree/spr_topology_test.cpp. Build target: spr_topology_test (see
CMakeLists.txt). It does not link the `main` library and never runs a real
IQ-TREE analysis pipeline, so most commands need no alignment or model --
the exception is the likelihood command below, which does load a real
alignment to actually evaluate the tree.

The hill-climbing search itself (command 5) lives in tree/sprsearch.{h,cpp}
rather than in spr_topology_test.cpp, because iqtree3 shares it: its
--spr-refine flag runs this same search as the refinement stage of its own
stochastic search, in place of NNI. See section 7 below. That split changed
no behavior here -- --hillclimb calls into the shared module instead of
owning it, and does exactly what it always did.


Running these commands
-------------------------
Paths below use forward slashes and no file extension, e.g.
build/spr_topology_test, run from the repo root (cd there first). On
Windows the binary is build/spr_topology_test.exe; forward slashes still
work unmodified in PowerShell, cmd.exe, and Git Bash. (Backslashes also
work in PowerShell/cmd.exe but not Git Bash, which treats \ as its escape
character -- build\spr_topology_test.exe there silently merges into a
nonexistent buildspr_topology_test.exe. Use forward slashes if unsure.)

The executable isn't installed or put on PATH, so always invoke it by
path -- build/spr_topology_test from the repo root, or ./spr_topology_test
from inside build/. It's statically linked, so running it needs no
special PATH/library setup on any platform (only building it does --
e.g. MSYS2/MinGW builds need mingw64 on PATH to build, not to run).

Quoting: examples use plain double quotes (e.g. "B,D", "RANDOM{yh/100}"),
which work as-is in PowerShell, cmd.exe, bash, and zsh.

Checking the last exit code: $? in bash/zsh, $LASTEXITCODE in PowerShell,
%ERRORLEVEL% in cmd.exe -- several commands here use the exit code to mean
something specific (e.g. --list-grafts returns 0 even with zero
candidates).

Build:
    cmake --build build --target spr_topology_test

Edge spec convention (used by every command that takes an edge argument):
    a comma-separated list of leaf names.
      - one name, e.g. C            -> that leaf's own pendant edge
      - two or more names, e.g. B,D -> the internal edge directly above
        the MRCA (most recent common ancestor) of those leaves
    Quote multi-name specs, e.g. "B,D", so the list arrives as one argument.

Tree argument convention (used by every command that takes a tree):
    a path to a Newick file, or a literal Newick string in quotes, e.g.
    "((A:0.1,B:0.1):0.1,C:0.1,D:0.1);"


1) Self-test
-------------
    build/spr_topology_test

    Runs the built-in regression test on a fixed hardcoded 6-taxon tree
    (mirrors test_scripts/test_data/spr/six_taxa.start.tree): applies one
    SPR move, checks the resulting adjacency/topology, rolls it back, and
    checks the tree is byte-for-byte identical to the original. Prints
    [PASS]/[FAIL] per check plus a final summary. Exit code 0 iff every
    check passed. No arguments; this is the default when no other mode
    matches.


2) Apply one SPR move
-----------------------
    build/spr_topology_test <tree> <prune-edge> <regraft-edge>

    Prunes <prune-edge> and regrafts it onto <regraft-edge>, printing the
    tree before and after. Does NOT roll back -- a one-shot "what would
    this move do?" check. Exit code 0 if the move was legal and applied, 1
    if rejected (illegal) or the tree/edges couldn't be read/resolved.

    Examples:
        build/spr_topology_test tree.nwk C D
        build/spr_topology_test tree.nwk C "B,D"
        build/spr_topology_test tree.nwk "B,D" "E,F"


3) List legal graft positions within a radius
-----------------------------------------------
    build/spr_topology_test --list-grafts <tree> <prune-edge> <radius>

    Prunes <prune-edge> and enumerates every distinct, legal regraft
    target within <radius> tree-hops of the prune point (see
    findGraftPositions in tree/spr_topology_test.cpp for exactly how
    radius/legality/dedup are defined). Pure enumeration, nothing is
    applied or mutated. Prints one line per candidate: its radius, its
    edge spec (feedable back into command 2 as a regraft-edge), and
    whether it's a pendant or internal edge. Exit code 0 even with zero
    candidates (a valid result, not an error); 1 only on a genuine input
    error (bad tree, unknown leaf name, etc).

    Example:
        build/spr_topology_test --list-grafts tree.nwk C 3


4) Compute the likelihood of a tree against an alignment
------------------------------------------------------------
    build/spr_topology_test --likelihood <tree> <alignment.fasta>

    Loads a real DNA or protein alignment -- sequence type auto-detected
    from content (Alignment::detectSequenceType), not read from a flag --
    and evaluates the log-likelihood of the given tree topology and branch
    lengths against it, under a plain fixed-parameter model (JC for DNA, LG
    for protein) with no rate heterogeneity and no optimization -- this
    reports the likelihood of the tree exactly as given, not the best
    achievable likelihood for that topology. Requires the alignment's
    sequence names to match the tree's leaf names exactly. Prints
    alignment/model summary (including the detected sequence type) plus the
    log-likelihood, along with IQ-TREE's normal alignment-reading
    diagnostics (composition/gap warnings etc., expected, not an error).
    Exit code 0 on success; 1 if the alignment file couldn't be opened; 2
    if the tree/alignment taxa don't match, the alignment is malformed, or
    its sequence type isn't DNA or protein (this tool doesn't handle
    binary/morph/codon/PoMo data).

    Examples (verified against real fixtures in test_scripts/test_data/):
        build/spr_topology_test --likelihood test_scripts/test_data/small.top.txt test_scripts/test_data/small.fa
        build/spr_topology_test --likelihood test_scripts/test_data/turtle.trees test_scripts/test_data/turtle.fa


5) Greedy randomized SPR hill-climbing search
------------------------------------------------
    build/spr_topology_test --hillclimb <alisim-tree.treefile> <radius> <max-steps> [random] [iqtreestart [N]] [starttree <path>] [model <spec>] [fast [N]] [quiet] [reopt] [fullreopt M N] [gtr] [record] [trajectory] [investigate [N]] [alternate] [shrink [N]] [learnradius [N]] [sweep [N]] [findopt [N]] [notree] [distradius] [weightprune]

    First, generate a ground-truth tree and a DNA alignment simulated
    along it with the full iqtree3 binary's built-in AliSim feature (a
    separate build target from spr_topology_test -- see "Generating input
    data" below):
        iqtree3 --alisim sim -m "GTR{2,4,1,1,4,2}+F{0.3,0.2,0.2,0.3}" -t "RANDOM{yh/100}" --length 10000 --seed 42 -af fasta

    (--seed is required. The rate/frequency parameters after GTR are
    required too, or AliSim silently defaults to all-equal exchangeability
    rates. Values above are arbitrary -- substitute whatever suits what
    you're testing. sim.treefile/sim.fa in the repo root were generated
    with this exact command.)

    This produces sim.treefile (the true tree) and sim.fa (the simulated
    alignment). Feed the .treefile to --hillclimb; the alignment path is
    derived automatically by replacing ".treefile" with ".fa" -- there is
    no separate alignment argument.

    The alignment's sequence type (DNA or protein) is auto-detected from
    its content (Alignment::detectSequenceType), not read from a flag, so
    a protein alignment/tree pair (from any source, not just AliSim -- the
    example above simulates DNA specifically) works the same way: JC
    becomes LG and GTR+FO becomes LG+FO throughout (see "gtr" below), with
    everything else about the search unchanged. Only DNA and protein are
    supported; any other detected sequence type (binary, morphological,
    codon, PoMo) is a fatal error.

    Algorithm: build a BioNJ estimate tree from the alignment's distance
    matrix (or a random Yule-Harding tree if "random", or
    buildIQTreeStyleStartTree's result if "iqtreestart"), then repeat up
    to <max-steps> times: pick a uniformly random prune edge via
    choosePrune(), pick a regraft target (every legal candidate within
    <radius> hops, scored exhaustively -- or N random chooseGraft() draws
    if "fast" is given), and keep the best-scoring candidate if it
    improves, otherwise roll it back. A non-improving step still counts
    toward <max-steps>; the search only stops early if the topology runs
    out of legal prune points entirely.

    Candidate likelihood scoring uses path-based partial-likelihood
    recomputation BY DEFAULT. For each trial SPR, dedicated scratch buffers
    replace only the directed partials changed by the rewired edges and by
    the path between the prune and graft positions; unaffected side-subtree
    partials remain cached. Trial rollback restores the original cache
    exactly. A locally improving winner is recomputed once using full cache
    initialization before it is committed, providing a correctness boundary
    and the valid baseline cache for the next step. A rejected winner rolls
    back without a full reset. No flag is needed to enable this behavior.

    Exception: "reopt" candidate scoring deliberately retains the previous
    full deleteAllPartialLh()+initializeAllPartialLh() path because its
    branch-length optimization performs broader cache invalidation.

    Optional trailing flags, any order (all but random/fast/quiet/gtr/
    record/starttree/model are EXPERIMENTAL -- informal testing found no
    measurable accuracy benefit over simpler alternatives, as noted
    per-flag):

      random         start from a random Yule-Harding tree instead of BioNJ
      iqtreestart [N] start from N (default 20) independent randomized
                     parsimony-addition trees, each lightly polished and
                     scored, keeping only the best -- mirrors real IQ-TREE's 
                     own multi-start preprocessing (IQ-TREE uses around 100).
                     Only changes where the search starts, not how it
                     searches from there. Scored under "gtr"'s model when
                     both are given. Mutually exclusive with "random".
      fast [N]       propose N (default 1) random chooseGraft() candidates
                     per step instead of exhaustively scoring every
                     candidate within <radius> -- much cheaper per step,
                     at the cost of not guaranteeing the radius's best move.

                     Leave N at 1. A step scores N candidates but applies
                     at most ONE move, so raising N pays N times over for a
                     single attempt; the same budget spent on N cheap steps
                     buys N chances to actually move. Measured on sim.fa
                     (100 taxa, 10k sites): raising N from 5 to 50 halved
                     the remaining gap to the optimum but cost 8.8x the
                     time -- the returns scale badly enough that more
                     ATTEMPTS beat more candidates per attempt at every
                     budget tried.
      quiet          suppress per-step output; only header + final summary
                     print (timing is CPU-clock, not wall-clock, so this
                     doesn't affect reported time either way -- it just
                     saves the per-line print cost on long runs)
      reopt          re-optimize (Newton-Raphson) the 4 edges around an SPR
                     move (the 3 it actually changes, plus the pruned
                     subtree's own upper edge, which now sits between a
                     different pair of neighbors) before scoring it, instead
                     of applySPR's naive placeholder lengths / that upper
                     edge's pre-move length; the whole starting tree is also
                     ML-optimized once up front. Noticeably slower/candidate
      fullreopt M N  independent of "reopt": run a full-tree
                     optimizeAllBranches(M) sweep every N SUCCESSFUL
                     (accepted) steps -- not every N steps attempted -- on
                     top of whatever "reopt" is or isn't doing per
                     candidate. Both M (round-count ceiling) and N
                     (successful-step interval) are REQUIRED, no default.
                     An optional third token, the
                     literal word "true" (e.g. "fullreopt 100 5 true"),
                     also ML-optimizes the whole starting tree up front.
                     No measurable accuracy benefit found over plain reopt
      gtr            search under GTR+FO instead of JC (matches sim.fa's
                     simulation model) for a DNA alignment, or LG+FO instead
                     of plain LG for a protein alignment (sequence type
                     auto-detected); only meaningful combined with
                     reopt/fullreopt/findopt, since JC/LG alone have no (or
                     fixed) model parameters to fit
      record         append this run's convergence trajectory (candidates
                     evaluated, wall time, current logL, gap to the true
                     tree's logL) to record_<model><tag>.csv in the repo
                     root, <tag> encoding which of fast/reopt/fullreopt/
                     investigate were also given (e.g.
                     record_JC_fast_reopt.csv). Appends across runs --
                     these files are never cleaned up automatically
      trajectory     independent of "record" -- needs neither. Writes the
                     tree's topology (no branch lengths) to its own
                     trajectory_<run-id>.nwk: one line right after the
                     starting tree is built, then one more after every
                     accepted step (never a reverted one, never a periodic
                     fullreopt/findopt refit). Each run gets its own file
      investigate [N] after any accepted move, re-prune the same point and
                     exhaustively search N (default 1) hops out, repeating
                     next step as long as each refinement keeps improving
      alternate      toggle every other step between a plain SPR search at
                     <radius> and an NNI-equivalent search at radius 1
      shrink [N]     replace the fixed <radius> with one that starts at
                     <radius> and narrows by 1 (floor 1) after N (default
                     10) consecutive non-improving steps
      learnradius [N] replace the fixed <radius> with one drawn fresh each
                     step from a Gamma distribution (method-of-moments fit,
                     spread capped -- see below) over the last N (default
                     20) successfully-accepted moves' own achieved radius,
                     mixed with a STARTING distribution in proportion to
                     how many of those N slots are filled so far.

                     <radius> is the MIDDLE of that starting distribution,
                     not a ceiling: it's a trapezoid on [0, maxPath] --
                     flat from 0 up to <radius>, then tapering LINEARLY
                     down to a density of exactly zero at maxPath (never
                     drawn) -- where maxPath is a structural limit, not a
                     tuned number: every edge the tree has (no simple path
                     can use more hops than that), or, composed with
                     "distradius", 100 (100% of the tree's own branch
                     length -- a budget that size can already reach
                     anywhere). With an empty history this trapezoid is
                     the WHOLE distribution; its own share shrinks in
                     direct proportion as successful moves accumulate, but
                     -- unlike an earlier version of this design -- never
                     reaches zero: even once N successes have landed, a
                     small, permanent minimum share of draws still comes
                     from it for the rest of the run, and the Gamma fit's
                     own spread is capped so it can never narrow all the
                     way down to a single value either. Together those two
                     floors mean the whole distribution keeps a genuine
                     chance to respond to new data for as long as the run
                     continues, rather than converging once and freezing:
                     if a real move keeps landing far from wherever the
                     fit has settled, that move's own achieved radius
                     still enters the window and can pull the fit back
                     into motion. The Gamma-fit component itself is NOT
                     capped at <radius> at all (unlike the starting
                     distribution's own middle) -- accumulated history can
                     legitimately push the learned radius past <radius>,
                     anywhere up to maxPath, if that's genuinely what's
                     paying off. From N successes on, the window slides,
                     continuously refitting over just the most recent N
                     rather than the run's entire history, so the learned
                     radius can also keep adapting if the search's own
                     favored radius drifts over a long run. Every
                     statistic involved (the window, its mean/variance,
                     the fitted shape/scale, the draw itself) is computed
                     in continuous (double-precision) terms throughout.

                     Composed with "investigate": since an investigation
                     attempt re-examines the SAME (node,dad) pair at a
                     different, fixed radius (investigateRadius) rather
                     than the step's own learned one, what feeds this
                     history is not any individual attempt's own local
                     radius, but ONE number per whole excursion -- the
                     initiating move plus every subsequent investigate
                     refinement that kept improving -- measured as the net
                     displacement from where the excursion started to
                     where it finally settled, recorded once the excursion
                     ends (the next investigation attempt fails to improve
                     or finds no legal candidate at all).

                     Composed with "distradius": the draw stays that
                     fractional percentage all the way into
                     chooseGraftByDistance -- NOT rounded to a whole number
                     first, unlike the plain hop-count case, which IS
                     rounded (to an integer) before reaching
                     findGraftPositions/chooseGraft, since a fractional hop
                     count has no meaning there. What gets fed back into
                     the window under "distradius" is also the equivalent
                     radiusPercent actually spent (chooseGraftByDistance's
                     own outPercentUsed, or, for an "investigate" excursion,
                     the real summed branch length of its path converted
                     the same way) -- NOT the walk-step/hop count
                     chooseGraftByDistance's outHops reports, which has no
                     fixed relationship to radiusPercent's own scale. This
                     is what lets the same machinery work regardless of
                     whether "radius" means a hop count (the normal case)
                     or, composed with "distradius", a percentage of branch
                     length -- see chooseGraftByDistance's own
                     outPercentUsed comment in the source for the full
                     reasoning. Mutually exclusive with "shrink" (both
                     replace the same step value via different,
                     incompatible mechanisms -- giving both is a parse
                     error, not silently resolved)
      sweep [N]      after the step loop finishes, rank every internal
                     edge by how well its current grouping is supported
                     relative to its two single-NNI alternatives
                     (adjacent_subtree_compatibility.pdf, sec. 8), then run
                     an exhaustive whole-tree regraft search on the N
                     (default 10) least-compatible edges, keeping each
                     improving move. Ranking is fixed, computed once (not
                     recomputed as sweep moves improve), so not guaranteed
                     SPR-optimal. Composes freely with every other flag
      findopt [N]    every N steps (default: once, at the end), run one
                     whole-tree ML refit on a scratch clone of the current
                     tree, always under the richest available model (GTR+FO
                     for DNA, LG+FO for protein) regardless of the main
                     search's own model -- purely diagnostic: the clone is
                     discarded after its logL is read, so the real search
                     is unaffected (pairs well with a cheap "fast quiet"
                     search, to see how much headroom remains). With
                     "record", each checkpoint writes its own row instead
                     of replacing the trajectory's final one, and "findopt"
                     is folded into the record filename's tag. Its CPU
                     cost is excluded from the run's own timing
      starttree <path>  start from this Newick tree (a file path, or a literal
                     Newick string) exactly as given -- both topology and
                     branch lengths are trusted as-is, unlike every other
                     starting-tree option here. Intended for e.g. the final
                     tree of a real iqtree3 NNI search already run on this
                     same alignment: skips BioNJ/random/iqtreestart entirely,
                     AND (unlike the plain BioNJ default) skips the up-front
                     full branch-length/model re-fit those need too -- with
                     "starttree", curScore is just tree.computeLikelihood()
                     on the given tree/model, no optimization of any kind
                     before the step loop starts. Mutually exclusive with
                     "random"/"iqtreestart" (three different ways to build
                     the SAME thing -- a starting tree -- so only one can be
                     given). Pairs naturally with "notree" (see below) to
                     search a real alignment starting from a real analysis's
                     own tree instead of this tool's own BioNJ estimate --
                     e.g.:
                       build/iqtree3 -s real.fa -st AA -m LG --prefix nni_run
                       build/spr_topology_test --hillclimb real.fa 10 10000 \
                           fast quiet notree starttree nni_run.treefile record
                     Plain "LG" here has no free parameters, so this already
                     matches nni_run's own model exactly with nothing further
                     to carry over. Fitting under "LG+FO" (ML-estimated amino
                     acid frequencies) instead needs "model" too -- see below
      model <spec>   build the tree's ModelFactory from this literal model
                     string (e.g. "LG+F{0.081,0.055,...}", 20 comma-separated
                     frequencies in the same A,R,N,D,C,Q,E,G,H,I,L,K,M,F,P,S,
                     T,W,Y,V order IQ-TREE's own .iqtree report prints its
                     "pi(X) = ..." lines in -- see alignment/alignment.cpp's
                     symbols_protein) INSTEAD of this run's own short
                     "LG"/"LG+FO" label. Doesn't affect that label itself --
                     record/run-id filenames still go by "gtr" as usual, see
                     buildRunId/recordSpreadsheetPath -- only which actual
                     model gets built. A "+F{...}" spec (fixed values, not
                     "+FO", which would still re-optimize from scratch) is
                     how real ML-fit parameters from an external run -- e.g.
                     iqtree3's own -m LG+FO -- get carried over rather than
                     either this tool's own un-fit "LG+FO" starting values or
                     having to refit them itself with no such external input.
                     Combine with "starttree"+"notree" so neither the
                     topology/branch-lengths NOR the model get re-derived:
                       build/iqtree3 -s real.fa -st AA -m LG+FO --prefix nni_run
                       (read the 20 "pi(X) = ..." lines under "State
                       frequencies:" in nni_run.iqtree, same A,R,N,...,V
                       order, into a comma-separated list)
                       build/spr_topology_test --hillclimb real.fa 10 10000 \
                           fast quiet notree starttree nni_run.treefile \
                           model "LG+F{<those 20 values>}" record
                     test_scripts/extract_iqtree_model.py automates the
                     "read nni_run.iqtree, build the spec string" step above
      notree         no ground-truth tree: <alisim-tree.treefile> is instead
                     a real alignment file path DIRECTLY (any file format
                     or sequence type Alignment can auto-detect --
                     FASTA/NEXUS/PHYLIP, DNA/protein; there is no ".fa"
                     derivation in this mode, unlike the normal AliSim
                     workflow). Skips the final RF-distance and true-tree-
                     logL output entirely; output.txt still gets the final
                     tree, just not a true tree or RF line. "record" still
                     works, writing NaN for the "gap to true tree" column
                     since there's no true tree to compare against. Every
                     other flag (starting tree method, radius, selection,
                     model, ...) works exactly the same as usual -- this is
                     for running the search on a real alignment you don't
                     have a known-correct tree for, not just AliSim output
      distradius     only affects "fast" mode's own candidate draws:
                     replaces chooseGraft's directed walk (a fixed number
                     of edge hops) with chooseGraftByDistance, which reads
                     <radius> as a PERCENTAGE of the tree's own total
                     branch length instead -- normalized, so the same
                     value means the same thing regardless of this
                     dataset's branch-length scale -- and walks by actual
                     summed branch length instead of hop count, stopping
                     ON whichever edge exhausts that budget (not the edge
                     before it). Sideways/backward hops refund the
                     distance of whatever edge they abandon rather than
                     spend it, since neither is real outward progress from
                     the prune point; a generous hop-count cap guarantees
                     the walk terminates regardless. No effect outside
                     "fast" mode. Composes with "learnradius" -- see its
                     own entry above
      weightprune    replace choosePrune's uniform random edge pick with
                     one weighted by each edge's own branch length instead
                     -- long branches are proportionally more likely to be
                     chosen as the prune edge than short ones, rather than
                     every edge being equally likely regardless of length.
                     Built as one cumulative-weight array over the whole
                     edge registry (the same cumulative-sum technique used
                     to weight graft distances), redrawn from with
                     upper_bound each retry attempt; falls back to the
                     ordinary uniform pick if every edge in the tree
                     happens to have zero length. A bare flag, no numeric
                     argument of its own. Independent of every other flag
                     here -- it only ever changes WHICH edge gets pruned,
                     never how the graft search that follows proceeds --
                     so it composes freely with "fast"/exhaustive,
                     "distradius", "learnradius", "investigate", etc.
                     EXPERIMENTAL -- see choosePrune's comment in the
                     source

    On completion (unless "notree"), prints the Robinson-Foulds (RF)
    distance between the original AliSim tree and the final tree, and
    writes both trees plus the RF distance to output.txt in the current
    directory (overwritten every run; with "notree", output.txt gets only
    the final tree). Also creates spr_hillclimb_tmp.* temp files (BioNJ's
    distance matrix and tree) unless starting from "random" or
    "iqtreestart". Exit code 0 on success (even with zero improving
    steps); 1 if the alignment couldn't be found (next to the tree file,
    unless "notree" -- then the path given is the alignment itself); 2 if
    its sequence type isn't DNA or protein.

    Examples:
        build/spr_topology_test --hillclimb sim.treefile 6 10
        build/spr_topology_test --hillclimb sim.treefile 6 10 random
        build/spr_topology_test --hillclimb sim.treefile 6 10 iqtreestart
        build/spr_topology_test --hillclimb sim.treefile 6 10 iqtreestart 50 gtr   (50-tree pool, scored under GTR+FO)
        build/spr_topology_test --hillclimb sim.treefile 6 10 fast 5              (5 candidates/step, keep the best)
        build/spr_topology_test --hillclimb sim.treefile 10 20 reopt
        build/spr_topology_test --hillclimb sim.treefile 10 20 fullreopt 100 5    (independent of "reopt")
        build/spr_topology_test --hillclimb sim.treefile 10 20 fullreopt 100 5 true (+ up-front whole-tree fit)
        build/spr_topology_test --hillclimb sim.treefile 10 20 fast quiet reopt gtr
        build/spr_topology_test --hillclimb sim.treefile 10 20 fast reopt gtr record  (-> record_GTR_FO_fast_reopt.csv)
        build/spr_topology_test --hillclimb sim.treefile 8 20 fast investigate
        build/spr_topology_test --hillclimb sim.treefile 8 20 fast alternate
        build/spr_topology_test --hillclimb sim.treefile 8 5000 fast shrink 15
        build/spr_topology_test --hillclimb sim.treefile 8 5000 fast learnradius       (Gamma-fit radius, window of 20)
        build/spr_topology_test --hillclimb sim.treefile 8 5000 fast learnradius 30    (same, window of 30)
        build/spr_topology_test --hillclimb sim.treefile 8 500 fast sweep 20
        build/spr_topology_test --hillclimb sim.treefile 6 500 fast quiet findopt record
        build/spr_topology_test --hillclimb sim.treefile 6 500 fast quiet findopt 100 record  (checked every 100 steps)
        build/spr_topology_test --hillclimb real_alignment.fasta 8 200 fast quiet notree      (no ground-truth tree; real_alignment.fasta read directly, any format/DNA-or-protein)
        build/spr_topology_test --hillclimb sim.treefile 10 200 fast quiet distradius         (radius = 10% of total tree length, not 10 hops)
        build/spr_topology_test --hillclimb sim.treefile 8 5000 fast distradius learnradius   (fractional percentage drawn each step, e.g. "radius 4.37")
        build/spr_topology_test --hillclimb sim.treefile 8 20 fast weightprune                (prune edge chosen proportional to its own branch length)

    Reference benchmark on the checked-in sim.treefile/sim.fa (100 DNA
    sequences, 10,000 sites): 400 paired fast-mode candidates took 0.578 CPU
    seconds locally versus 10.469 seconds with full resets (18.108x faster),
    with maximum absolute logL difference 2.33e-10 (floating-point noise, not
    a correctness issue). An exhaustive run over 386 paired candidates
    measured 0.469 versus 10.125 seconds (21.600x). See
    PARTIAL_LIKELIHOOD_ATTEMPT.md for the root cause of the earlier
    incorrect attempts and how this one differs.


6) Same-random-moves branch-length comparison (NOT a search)
---------------------------------------------------------------
    build/spr_topology_test --branchlength-compare <alisim-tree.treefile> <radius> <max-steps>

    Same input files/conventions as --hillclimb (command 5). Applies the
    SAME sequence of random SPR moves to four copies of one starting tree,
    differing only in how each move's branch lengths are set:
      A: applySPR's naive placeholder lengths (the default everywhere else
         in this tool absent "reopt")
      B: re-optimizes (Newton-Raphson) just the 4 edges around each move
      C: re-optimizes EVERY edge, one full optimizeAllBranches() sweep/move
      D: same as C, but up to 10 full sweeps per move
    All four start from an identical, fully branch-length-optimized random
    Yule-Harding tree, and every candidate is accepted unconditionally on
    all four (a random walk, not a search), so any divergence in their
    logL trajectories comes only from branch-length handling, never from
    different topological paths.

    choosePrune()/chooseGraft() can't be called independently per copy
    (they'd desync against the shared RNG stream), so each step instead
    draws one shared prune-edge slot and one shared regraft-candidate
    index and applies the corresponding move to all four copies (see
    runBranchLengthCompare's comment in tree/spr_topology_test.cpp for the
    full mechanism; a sync mismatch aborts the run rather than continuing
    on a nonsense comparison).

    Prints step,logl_diff_a,logl_diff_b,logl_diff_c,logl_diff_d to stdout,
    and a fuller version (logl_before/after/diff for all four copies) to
    branchlength_compare_data.csv (repo root, overwritten each run).
    Copies C and D are much more expensive per step than A/B (a full sweep
    touches every edge, not just 3), so this command is slow.

    Expect much larger |diff| in the first few steps than later ones, on
    all four copies: the starting tree begins at a likelihood peak (just
    ML-fit), so an unweighted random move overwhelmingly lands somewhere
    worse, often sharply; once knocked off the peak, later steps fluctuate
    around the flatter likelihood level generic trees occupy. This is
    expected behavior of an unconditional random walk from an optimum, not
    a bug.

    Example:
        build/spr_topology_test --branchlength-compare sim.treefile 6 50


7) Using this SPR search inside iqtree3's own stochastic search
------------------------------------------------------------------
    build/iqtree3 -s <alignment> -m <model> --spr-refine "<flags>"
    build/iqtree3 -s <alignment> -m <model> --nni-refine "<flags>"

    These are iqtree3 flags, not spr_topology_test ones -- but the string
    they take is written in exactly the vocabulary command 5's trailing
    flags use, and is parsed by the same code (tree/sprsearch.cpp's
    parseRefineSpec). The two tools deliberately share one flag language
    rather than maintaining two that can drift.

    What they change
    ------------------
    IQ-TREE's stochastic search is an iterated local search: each
    iteration perturbs the current tree (doTreePerturbation -- random NNIs
    on a tree drawn from the top of the candidate set), then hill-climbs
    back up, then keeps the result only if it survives the candidate set.
    "--spr-refine" replaces the hill-climb half -- normally doNNISearch --
    with this file's own SPR search, run through the shared module
    tree/sprsearch.h. Everything else about the iteration is untouched:
    the same perturbation, the same candidate set, the same stopping rule,
    the same model re-optimization on an improving iteration.

    Without either flag, iqtree3 behaves exactly as it always has, and
    spr_topology_test --hillclimb (command 5) is likewise unchanged --
    all three are separate, fully working modes.

    "--nni-refine" keeps the default NNI hill-climb but turns on the
    reporting flags below, so an NNI-refined run and an SPR-refined run
    can be compared in the same spreadsheet format. It is the only reason
    to pass it: "--nni-refine """ is exactly the default.

    Which flags apply
    -------------------
    Accepted by BOTH --spr-refine and --nni-refine (these describe what
    gets reported, not how a step is chosen):

      quiet          suppress the per-step output
      record         append this run's convergence trajectory to
                     record_<model><tag>.csv, same format and same
                     appending behavior as command 5's own "record". The
                     tag names the refiner, so the two never share a file:
                     record_LG_spr_fast_learnradius.csv vs
                     record_LG_nni.csv. The "gap to the true tree" column
                     is NaN throughout -- a real analysis has no
                     ground-truth tree, exactly as under "notree"
      trajectory     one Newick line per completed iteration in
                     trajectory_<run-id>.nwk
      findopt [N]    the diagnostic whole-tree ML refit on a throwaway
                     clone, read for its logL and discarded. Its cadence
                     counts PERTURBATIONS here, not SPR steps: one refit
                     every N kicks (default: every kick). Unlike command
                     5, the refit uses THIS run's own model rather than
                     the tool's GTR+FO/LG+FO default, since -m may well
                     name something richer and a headroom figure measured
                     under a weaker model would read as negative

    Accepted by --spr-continuous only:

      escape S T     escape a stalled search WITHOUT restarting it. Once S
                     consecutive steps pass with no improvement, the
                     current tree and score are saved, a deliberately
                     negative random kick is applied, and T steps are spent
                     trying to beat the saved score. Beat it and the
                     excursion is kept; fail and the tree is rolled back
                     exactly, as though the kick never happened. The stage
                     gives up after 20 consecutive failed excursions, or
                     when "steps N" runs out.

                     This is IQ-TREE's own perturb-then-refine loop moved
                     INSIDE one continuous SPR run. The difference is where
                     a failed attempt lands: IQ-TREE restarts from a tree
                     drawn out of the candidate set, whereas this reverts
                     in place, so the search never gives up ground it has
                     already won.

                     The kick itself is whichever one the run is
                     configured for -- --spr-perturb's random SPRs if that
                     flag is given, otherwise IQ-TREE's own random-NNI kick
                     -- at the same floor((ntaxa - 3) * --perturb) strength
                     either way, so kick strength stays a single setting.
                     Escaping runs get their own record file (the tag
                     carries "_escape").

    Top-level iqtree3 flags added alongside these (neither belongs to a
    refine/perturb spec string -- both are their own CLI flags):

      --perturb-slack D [anneal]
                     the kick-agnostic spelling of --spr-perturb's "slack".
                     Bounds one PERTURBATION move's damage to D
                     log-likelihood, whichever kick is running: with
                     --spr-perturb it bounds the SPR kick, and WITHOUT it
                     bounds IQ-TREE's own default random-NNI kick. That is
                     the only way to get the behaviour on the NNI kick, so
                     the same bound can be compared across both. "anneal"
                     decays D to 0 across the first min_iterations kicks.
                     Refused draws are rolled back and redrawn (up to 8
                     attempts per slot), so a kick still lands its full
                     move count wherever it can.

      --accept-dist ["SPEC"]
                     replace the REFINEMENT's strict improve-only rule with
                     a stochastic one, AND suppress the perturbation stage
                     entirely. A move losing |dL| is kept with probability

                         P = exp(-(|dL| / T)^shape)

                     while any improvement is kept outright (P = 1). So the
                     whole (-inf, 0) side of the likelihood-change axis is a
                     tunable curve and [0, inf) is flat at 1.

                     SPEC is any of, in any order:
                       temp T     the tolerable-loss scale (default 0.5)
                       shape S    falloff exponent (default 1)
                       anneal     decay T toward "floor" over the run
                       floor F    lowest T annealing may reach (default 0)

                     shape = 1 is the classic Boltzmann/Metropolis rule;
                     shape = 2 stays near 1 well inside T then falls off a
                     cliff; shape -> infinity becomes a hard threshold at
                     |dL| = T, which is exactly what "slack" does -- so
                     slack is the limiting case of this same family rather
                     than an unrelated idea.

                     The default T = 0.5 is chosen for FINAL CONVERGENCE
                     rather than exploration: a move 0.5 worse is kept with
                     P = 0.37, one 2 worse with P = 0.018, one 5 worse with
                     P = 4.5e-5. Small backward steps that let the search
                     round a barrier are admitted; genuinely destructive
                     moves effectively never are. Raise T to explore. With
                     "anneal" and the default floor of 0 the run ends as a
                     strict hill-climb no matter how it started, which is
                     the point: the walk converges rather than wandering.

                     Because accepted downhill moves let the CURRENT tree
                     drift below the best one seen, the best topology is
                     tracked and restored before the result is reported --
                     the run never reports wherever the walk happened to
                     stop.

                     Applies to BOTH refiners at each one's own accept/
                     reject point: the SPR step loop's keep/revert test, and
                     the NNI refiner's evaluateNNIs filter. It composes with
                     --spr-refine (SPR refinement) or the default NNI
                     refinement without further configuration.

    Accepted by --spr-perturb only -- these shape the KICK, parsed by
    sprsearch.cpp's parsePerturbSpec rather than parseRefineSpec:

      radius N       how far the kick's SPR draws reach (default 6). Same
                     meaning as command 5's positional radius
      distradius     kick draws use chooseGraftByDistance (radius read as
                     a PERCENTAGE of the tree's total branch length)
                     instead of a fixed hop count -- same meaning as
                     --spr-refine's own "distradius"
      weightprune [long]  bias which edge the kick prunes from, same
                     weighting command 5's "weightprune" uses ("short" is
                     deprecated -- see the retired-experiments note below)
      slack D [anneal]  bound how much worse a single kick move is allowed
                     to make the tree. Without it, --spr-perturb's moves
                     are applied blind: no score is consulted, so a kick's
                     total damage is unbounded (floor((ntaxa-3)*--perturb)
                     moves, each free to land anywhere). With "slack D",
                     each proposed move is scored, and kept only if it
                     costs at most D log-likelihood versus the tree before
                     that move; a costlier draw is rolled back and another
                     target is tried (up to 8 redraws per slot, then that
                     slot is given up on rather than spinning forever).
                     The idea is to keep the kick inside a basin the
                     refinement stage can still climb back out of, rather
                     than letting it wander anywhere at all.

                     "anneal" decays D linearly from its given value down
                     to 0 across the run's first min_iterations kicks (the
                     -n/--ninit-derived iteration count IQ-TREE would
                     otherwise stop at by default), then holds at 0 --
                     i.e. early kicks are more exploratory and later ones
                     barely disturb the incumbent at all. Without
                     "anneal", D is constant for the whole run.

                     This is strictly a perturbation-side flag: passing it
                     to --spr-refine or --nni-refine is an error, since
                     accepting a downhill move inside the HILL-CLIMB would
                     let a non-improving tree leak into what the search
                     reports. (Contrast "tunnel", a --spr-refine-only flag
                     that tolerates a downhill move inside the hill-climb,
                     but only transiently, while a paired follow-up move is
                     being tested, and never keeps it alone.)

                     Every kick prints one summary line: how many moves
                     were applied vs. refused, over how many kicks, and
                     the effective delta (after annealing, if used) on the
                     kick that just ran.

    Accepted by --spr-refine only -- these shape an individual SPR step,
    and mean exactly what they mean in command 5:

      radius N       the step radius (default 6). Positional in command 5;
                     a named flag here, since there is nowhere positional
                     to put it
      steps N        cap one refinement pass at exactly N SPR steps. WITHOUT
                     it (the default) a pass instead climbs to a local
                     optimum the way the NNI refinement it replaces does --
                     running in blocks of (ntaxa - 3) steps and stopping
                     once a whole block fails to improve. That matters:
                     the perturbation applies floor((ntaxa - 3) * --perturb)
                     random NNIs, 48 of them on a 100-taxon tree at the
                     default strength, so a fixed budget that runs out
                     before those are undone hands the candidate set a tree
                     far WORSE than the one it was kicked from, and the
                     search goes backwards. Give "steps N" only when you
                     specifically want a fixed budget
      fast [N]       N random chooseGraft() draws per step instead of
                     exhaustively scoring the radius
      reopt          Newton-Raphson on the 4 edges around each candidate.
                     Turns on IQ-TREE's safe numerical scaling (-safe) for
                     the whole run, as spr_topology_test does for the same
                     flag: a real branch-length search can push a length to
                     an extreme the plain kernel underflows on. Note this
                     also disables the partial-likelihood cache (that path
                     invalidates too broadly), so candidates cost roughly
                     20x what they do without it
      fullreopt M N  periodic whole-tree optimizeAllBranches sweep. Its
                     optional third "true" token is NOT accepted -- that
                     is an up-front fit of the STARTING tree, which is
                     IQ-TREE's own job (see the rejected list below)
      investigate [N], alternate, shrink [N], learnradius [N],
      distradius, weightprune, sweep [N]
                     all as documented in command 5. "sweep" runs once at
                     the very end of the whole IQ-TREE search, over the
                     final tree -- it is an end-of-run phase there too,
                     not something to repeat per perturbation

    Rejected, in both modes, with an error naming the IQ-TREE option that
    already owns the job. These configure a whole standalone run rather
    than a refinement pass, and silently ignoring one would leave you
    believing it took effect:

      random, iqtreestart, starttree    -> IQ-TREE's own -t / --ninit
      model, gtr                        -> IQ-TREE's own -m
      notree                            -> always implied; there is never
                                           a ground-truth tree here

    --spr-refine additionally refuses, up front, the tree shapes its
    machinery is not written against: rooted trees, partition models
    (-p/-q), PLL (use -nopll), and any sequence type other than DNA or
    protein. Each is reported at startup, before the run spends anything
    on model fitting.

    Reading the record CSV
    ------------------------
    The "candidates evaluated" column is the x-axis both refiners share.
    For SPR it counts scoreTrialSPRMove calls (one per trial regraft); for
    NNI it counts scored alternative topologies (two per branch that
    evaluateNNIs examines, since getBestNNIForBran scores both). Same
    unit, so the two trajectories plot against each other directly.

    Examples:
        build/iqtree3 -s real.fa -m LG --spr-refine "radius 10 fast quiet"
        build/iqtree3 -s real.fa -m LG --spr-refine "radius 10 fast learnradius 30 record"
        build/iqtree3 -s real.fa -m LG --spr-refine "fast weightprune steps 200 record"
        build/iqtree3 -s real.fa -m LG --nni-refine "record findopt 25"
        (the last two produce record_LG_spr_fast_weightprune.csv and
         record_LG_nni_findopt.csv -- directly comparable)



Retired experiments and their findings
-------------------------------------------
Tried, found not to earn their keep, and removed. Kept as a pointer for
anyone tempted to re-add them.

  Parsimony prescreen (--hillclimb's old "prescreen" flag): auto-reject a
  candidate on a cheap parsimony score before checking real likelihood, if
  clearly worse (tolerance hardcoded to 2 substitutions). No consistent
  speed/RF benefit found -- and a bug found afterward
  (computeParsimony() silently returned 0 for every tree, since
  Alignment::orderPatternByNumChars() was never called) meant prescreen
  had never actually rejected anything during testing: prior results were
  pure RNG noise. Fixed but never usefully retested; removed.

  --randomwalk: unconditional-acceptance SPR random walk from a random
  start, to measure how a candidate's parsimony difference relates to its
  likelihood/RF difference without --hillclimb's improve-only bias.
  Finding (sim.treefile, ~100 taxa/3000bp, JC, radius 10, 2000 steps):
  parsimony difference correlates moderately with likelihood difference
  (Pearson r = -0.56; a reject-if-diff > T rule gets ~69% classification
  accuracy for T in about -15..+2, vs. 53% baseline). Said essentially
  nothing about RF difference (random start was already near-maximum RF
  distance; a single move almost never changed it, 14/1869 steps).

  --randomwalk-subtree: same walk, testing a different proxy -- the local
  subtree spanning the prune/graft positions, evaluated standalone vs. the
  whole tree's likelihood change. Finding (same dataset, radius 10, 1000
  steps/489 measured): STRONG correlation (Pearson r = 0.87, 82% sign
  agreement), far better than the parsimony proxy -- but the
  implementation was slower (1.3x-3.7x) than just evaluating the whole
  tree, since rebuilding a standalone PhyloTree/Alignment/ModelFactory
  every step cost more than the likelihood math it saved. Not worth using
  as implemented; a cheaper implementation (reusing partial-likelihood
  buffers on the existing tree instead of new objects) might still pay
  off but was judged too risky to get right without extensive testing.

  --hillclimb's old "massapply [N]" flag: applied a batch of N independent
  SPR moves for real with no intermediate check, then one likelihood
  evaluation decided whether to keep or revert the whole batch (reverting
  in reverse order). Removed without a rigorous comparison against plain
  "fast" ever completed -- record_JC_fast_massapply.csv (repo root) has
  one informal run's trajectory if anyone wants to revisit it.

  --hillclimb's old "iqtreestart ... real" flag: scored the "iqtreestart"
  candidate pool with real IQ-TREE's own IQTree::optimizeBranches
  (tree/iqtree.cpp) instead of this tool's own PhyloTree::optimizeAllBranches,
  otherwise the same hand-driven pool loop as plain "iqtreestart". Getting
  there surfaced two real segfaults: params.pll defaults to true whenever
  this project is built with PLL support, and IQTree::optimizeBranches
  branches on it, taking a PLL code path against an uninitialized
  pllInst/pllPartitions this tool never sets up (worked around by forcing
  params.pll = false); and calling IQTree::initCandidateTreeSet directly
  (tried first, as a single call replacing the whole pool loop) turned out
  to also run real NNI moves internally via doNNISearch on the top
  params.numNNITrees candidates before ever returning, which needs a
  Checkpoint wired into the model, not just the tree, to avoid crashing --
  judged out of scope, so the pool loop was kept hand-driven instead,
  calling only the per-candidate primitives (computeParsimonyTree,
  optimizeBranches), never initCandidateTreeSet itself. Finding
  (sim.treefile/sim.fa, pool 20, GTR+FO): fastest of every iqtreestart
  variant tried (61.2s CPU vs. 73.1s for the plain, tuned pool loop), but
  worst starting-tree quality of the bunch (logL 134.3 below the true
  tree's, vs. 35.8 for the tuned loop -- worse even than the very first,
  unoptimized iqtreestart's 126.3). IQTree::optimizeBranches's own
  tolerance/step-cap constants (params->loglh_epsilon, PLL_NEWZPERCYCLE)
  are evidently tuned assuming the doNNISearch polish that always follows
  it in a real analysis, which this mode deliberately never ran. Removed.


Generating input data with AliSim
----------------------------------
--hillclimb needs the FULL iqtree3 executable (a separate CMake target) to
generate its input, since AliSim lives in main/alisim.cpp, which
spr_topology_test deliberately doesn't link (see the header comment in
tree/spr_topology_test.cpp for why). Build it once:
    cmake --build build --target iqtree3

Then generate a tree+alignment pair, e.g. 100 taxa, Yule-Harding random
tree, GTR model with explicit rates/frequencies, 10000bp (the exact
command used to generate the sim.treefile/sim.fa checked into the repo
root, minus the taxon count):
    build/iqtree3 --alisim sim -m "GTR{2,4,1,1,4,2}+F{0.3,0.2,0.2,0.3}" -t "RANDOM{yh/20}" --length 10000 --seed 42 -af fasta -redo

--seed is required (any integer, for reproducibility). -redo is only
needed if sim.treefile/sim.fa already exist from a previous run in the
same directory. Both generated files land in the current directory.

The GTR{...}+F{...} parameters aren't cosmetic -- omitting them (plain
"-m GTR") makes AliSim default to all-equal exchangeability rates (no more
complex than JC) and print warnings recommending explicit parameters. Rate
order for GTR{...} is AC,AG,AT,CG,CT,GT and F{...} is A,C,G,T; the values
above are arbitrary but explicit, which is what avoids the warnings --
substitute whatever rate/frequency skew suits what you're testing.

iqtree3 is statically linked (same as spr_topology_test), so it runs
standalone with no PATH setup needed on any platform.


Notes
-----
- Branch lengths print with 1 decimal place in all Newick output from this
  tool (see newickOf() in tree/spr_topology_test.cpp) -- a display
  setting for readability, not a precision limit on computation.
- If your Newick input has no branch lengths at all, IQ-TREE's parser
  defaults them to a -1.0 sentinel; applySPR's naive half-split of a
  target edge's length then propagates that sentinel into negative-
  looking lengths in the output. Use a tree with real branch lengths for a
  readable demo/result.
- Grafting onto the edge incident to the tree's arbitrary root leaf (an
  internal bookkeeping node, not a real taxon in the rooted-input case) is
  always rejected as illegal by isLegalSPR, however you specify it (single
  leaf name, or a multi-leaf spec that resolves to that same edge).
- After every applySPR/rollbackSPR call that will be followed by a
  computeLikelihood(), this tool calls resetLikelihoodBuffers() (a full
  deleteAllPartialLh()+initializeAllPartialLh() pair), not just
  clearAllPartialLH(). Plain clearAllPartialLH() only marks existing
  per-edge buffers stale, relying on IQ-TREE's incremental buffer-reuse
  bookkeeping to know which buffer belongs to which edge -- an invariant
  NNI maintains (only ever touches edges adjacent to an already-evaluated
  branch) but SPR does not (a regraft can jump to a distant edge).
  Skipping this crashes nondeterministically with a buffer-reorient or
  buffer-aliasing assertion, depending on the memory-saving mode in effect.
- To run an inbuilt NNI test: iqtree3 -s sim.fa -m GTR
- To record iqtree3's own built-in stochastic NNI search (not
  spr_topology_test's SPR API) into record_<model>_iqtree_nni_ownstart.csv
  (same columns as --hillclimb's "record" flag; own BIONJ/parsimony start
  -- sim.treefile is only used afterwards, in a separate -te run, for the
  true_minus_current reference column, never fed to the search itself;
  full wall-clock timing corrected for IQ-TREE's own per-iteration "Time:"
  field only starting once its own start tree exists -- see the script's
  header comment for why):
    test_scripts/record_iqtree_nni.sh <alisim-tree.treefile> <nstop> [gtr] [quiet]
    (or record_iqtree_nni.ps1, same behavior, for PowerShell)

  Examples:
    test_scripts/record_iqtree_nni.sh sim.treefile 100
    test_scripts/record_iqtree_nni.sh sim.treefile 100 gtr quiet

- To find the RF distance between sim.treefile and sim.fa.treefile:
    build/iqtree3 -t sim.treefile -rf sim.fa.treefile -pre rf_check 2>&1 | tail -5
    cat rf_check.rfdist
    rm -f rf_check.rfdist rf_check.log
